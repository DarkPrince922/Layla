# Проектные skills и command hooks

Функции подключены к Code и его независимым воркерам. Они не подключаются к
остальным доменам. Это поэтапный перенос: полное соответствие архиву ещё не
достигнуто.

## Skills

### Встроенные skills Layla

В Code доступны три встроенных workflow, даже если в проекте нет `.layla/skills`.
Они отображаются в кнопке **Skills** с пометкой **Встроенный** и вызываются
обычными slash-командами:

| Команда | Назначение |
|---|---|
| `/simplify [область]` | Проверка изменений на повторное использование, качество и эффективность, затем обоснованные исправления и подходящие проверки |
| `/skillify [процесс]` | Создание `.layla/skills/имя/SKILL.md` из текущей работы, с аргументами, шагами и критериями готовности |
| `/remember [область]` | Обзор заметок текущего Code-чата и правил проекта: дубли, конфликты, устаревшие сведения и предложения переноса |

`/simplify` может вызываться моделью. Ведущий использует до трёх свободных слотов
для read-only ревьюеров; при занятых слотах выполняет оставшиеся проверки сам.
Воркер проводит проверки самостоятельно, без рекурсивной делегации. Исправления
делает ведущий; commit/push/PR не создаются только из-за вызова этого skill.

`/skillify` и `/remember` требуют явного slash-вызова пользователя.
`/skillify` уточняет существенные пробелы через `ask_user`, читает встроенный
шаблон и может писать только внутри `.layla/skills/**`. Новый skill виден
со следующего запроса, поскольку текущий каталог остаётся снимком.
В Plan или без права записи возвращается черновик.
`/remember` имеет только инструменты чтения и вопросов: предложения не меняют
память или файлы. Пользователь может одобрить конкретные изменения следующим
сообщением. Глобальные, командные и чужие чатовые источники не подключаются.

Все skills сохраняют ограничения режима, персоны и Confirm. Это инструкции
для агента, а не отдельные жёстко запрограммированные исполнители; результат
работы и проверки должны подтверждаться инструментами.

Тексты и шаблон поставляются в Python-пакете Core, не копируются в проект.
`read_skill` читает их по имени; шаблон —
`read_skill(name="skillify", file="templates/SKILL.md")`. Поле `source` каталога
равно `bundled`; виртуальный `path` начинается с `bundled://layla/` и не является
путём файлового API. Ресурсы ограничены встроенным manifest, выход к файлам
Core/проекта через этот reader недоступен. CI проверяет чтение из собранного wheel.

### Проектные skills

Поиск идёт в таком порядке, первое найденное имя имеет приоритет:

1. `.layla/skills`;
2. `.claude/skills`;
3. `.agents/skills`;
4. `.layla/commands`;
5. `.claude/commands`.

Поддерживаются `имя.md` и `имя/SKILL.md`, а также вложенные namespaces:
`.claude/commands/ops/deploy.md` даёт `/ops:deploy`. Каталог с `SKILL.md`
считается одним skill; соседние файлы служат ресурсами, не slash-командами.
На первом обращении к пути читаются skills всех его каталогов-предков;
ближайший каталог перекрывает корневое имя. Соседняя подпапка не наследует
этот override. Vendor/build-каталоги не обходятся. Невалидная версия с высоким
приоритетом не заменяется молча версией из другой папки. Ссылки не читаются.
Имена состоят из максимум восьми сегментов по 80 символов из латиницы, цифр,
точки, дефиса и подчёркивания, разделённых `:`.

Одноимённый проектный skill имеет приоритет над встроенным в своей области.
При ошибке проектного frontmatter встроенная версия не включается молча.

В Code кнопка **Skills** загружает каталог текущего проекта и вставляет `/имя`
в черновик сообщения. Выбор привязан к текущей рабочей копии; поле пути
позволяет открыть вложенный каталог. Выбранный путь сохраняется в черновике
и передаётся при запуске slash-команды. Она не запускает задачу автоматически. Можно написать
`/имя аргументы` вручную. Каталог API — `GET /api/projects/{id}/skills`, с
проверкой владельца; параметр `?path=src` выбирает область. Worktree API:
`GET /api/projects/{id}/chats/{chat_id}/workspaces/{workspace_id}/skills`.
Тело инструкций через каталог не возвращается.

Агент видит доступные workflows и вызывает `invoke_skill` с `name` и `args`.
`read_skill` читает снимок файла, а `invoke_skill` применяет его метаданные.
У обоих есть необязательный `path`. `read_skill(file="scripts/check.py")`
читает вспомогательный файл относительно каталога skill; список ресурсов
возвращается при чтении самого skill. Вспомогательные файлы читаются в их
текущем состоянии, тело и frontmatter skill фиксируются на первом обнаружении.
`invoke_skill` остаётся доступен и при пустом корневом каталоге, чтобы модель
могла обнаружить вложенные skills позже.

| Поле frontmatter | Поведение |
|---|---|
| `name` | Человекочитаемое имя; slash-имя определяется файлом/папкой |
| `description`, `argument-hint`, `when_to_use` | Описание, подсказка и назначение в каталоге; без description используется первый абзац |
| `paths` | Glob-набор относительно каталога-предка; модель видит skill после обращения к подходящему пути, пользователь может выбрать явно |
| `arguments` | Список или строка имён аргументов |
| `disable-model-invocation: true` | Модель не активирует skill самостоятельно; нужен пользовательский `/имя` |
| `user-invocable: false` | Skill скрыт из пользовательского выбора и не вызывается через slash |
| `allowed-tools` | Имена и ограничения аргументов; сужает инструменты агента на текущий запуск |
| `context: fork` | Создаёт обычного независимого worktree-воркера |
| `agent` | `Explore`/`Plan`/`explore`, `review`, `implement`/`general-purpose` |
| `model` | `inherit` или точное имя включённой модели текущего провайдера; провайдер и credentials не меняются |
| `effort` | `low`, `medium`, `high`, `max`; передаётся как reasoning_effort |
| `shell` | `bash` по умолчанию либо доступный в sandbox `powershell` для динамических команд |
| `hooks` | Hooks, активные до конца этого запуска/воркера |

Аргументы разбираются с кавычками. `$ARGUMENTS` означает всю строку,
`$ARGUMENTS[0]` и `$0` — первый аргумент, `$1` — второй; `$имя` использует
имена из `arguments`. `${CLAUDE_SKILL_DIR}`/`${LAYLA_SKILL_DIR}` дают
относительный каталог skill, `${CLAUDE_SESSION_ID}`/`${LAYLA_SESSION_ID}` —
идентификатор чата или воркера. Подстановка однократная и буквальная:
`$()`, обратные кавычки и вложенные placeholders из аргументов не исполняются.
Если placeholders отсутствуют, аргументы добавляются как текст `ARGUMENTS:`.

`allowed-tools` принимает имена Layla и распространённые имена архива:
`Read`, `Write`, `Edit`, `Glob`, `Grep`, `Bash`, `Agent`/`Task`, `Skill`, `LSP`,
`TodoWrite`, `TaskCreate/Get/List/Update`, `TaskOutput`, `TaskStop`.
Доступны `Read(src/**)`, `Write(...)`, `Edit(...)`, `NotebookEdit(...)`,
`Glob(...)`, `Grep(...)`, `Agent(Explore)`/`Task(implement)` и `Bash(git status:*)`.
Файловые ограничения относятся к аргументу пути относительно корня проекта.
Bash принимает одну простую команду: точное совпадение токенов или префикс
токенов с суффиксом `:*`; pipes, redirects, compound и command substitution
отклоняются. Это ограниченный синтаксис, не общий shell parser/permission engine.
Список пересекается
с возможностями персоны и режима, не даёт новых прав. Последующие skills
могут только сузить текущий scope, а не расширить его. Ограничение действует
до конца запуска; это отличается от архивных добавочных разрешений.

`context: fork` использует тот же лимит трёх активных воркеров. В Plan/Review
создаётся исследователь без записи; в Confirm запуск воркера подтверждается.
Ограничения имён и аргументов сохраняются в его состоянии и после resume.
Повторная активация внутри воркера также сохраняет новые ограничения, модель,
effort и hooks. Несколько политик пересекаются, а не заменяют друг друга.
Воркеры не создают других воркеров. Основной проект меняется только через
обычный проверяемый импорт `worker_apply`, с дифами и checkpoints.

Переопределение модели действует только в этом запуске/воркере, включая смену
worktree/режима; настройка модели чата не меняется. В Confirm изменение
модели/effort подтверждается. Disabled/неизвестная модель отклоняется до команд.
Token/USD учёт и изученные capabilities относятся к фактически вызванной модели.
При смене модели несовместимые reasoning/thinking блоки удаляются из replay,
при этом исходный журнал сохраняется.

## Динамический контекст skill

В теле skill поддерживаются явные `!` перед inline code (`!` + backtick +
команда + backtick) и fenced-блоки с info `!`. Например строка в SKILL.md:

~~~markdown
Изменения: !`git status --short`
~~~

Только эти сегменты исходного файла становятся командами. Маркеры из аргументов,
вывода, обычных code fences и HTML-комментариев не сканируются повторно.
Аргументы передаются через безопасно установленные переменные среды, а не как
новый shell-код; в команде используйте кавычки вокруг `$ARGUMENTS`/`$target`.
Обработка выполняется обычным `run_command` в sandbox: project Pre/Post hooks,
Confirm, timeout, ограничения персоны/skill и возврат файлов через diffs и
checkpoints сохраняются. Собственные hooks skill регистрируются после успешной
активации; для fork они принадлежат дочернему воркеру.

Plan/Review не исполняют динамические команды. После ошибки, отказа или начала
выполнения повтор той же пары путь skill/аргументы в этом запуске блокируется;
после прерывания/рестарта следует проверить сохранённый результат до повтора.
Лимит — 8 команд, 24000 символов команд, по 8000 символов вывода; эти вызовы
учитываются в общем лимите инструментов. Вывод помечен как недоверенные данные.

## Конфигурация hooks

Источники, от низкого приоритета к высокому:

1. `.claude/settings.json`, `.claude/settings.local.json`;
2. `.layla/settings.json`, `.layla/settings.local.json`;
3. `.layla/hooks.json`.

Группы одного события из более высокого источника заменяют группы этого
события. Hooks активированных skills добавляются на время запуска. Флаг
`disableAllHooks: true` отключает и проектные, и добавляемые skill hooks.

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Write|Edit|delete_file",
      "hooks": [{
        "type": "command",
        "command": "python .layla/check_change.py",
        "timeout": 30,
        "once": false
      }]
    }]
  }
}
```

Поддерживаются только command hooks:

| Событие | Момент |
|---|---|
| `SessionStart` | Начало выполнения запроса: `source=startup` или `resume` |
| `UserPromptSubmit` | До первого вызова модели |
| `PreToolUse` | До действия, подтверждения и создания checkpoint |
| `PostToolUse` | После успешного результата инструмента |
| `PostToolUseFailure` | После результата с ошибкой |
| `Stop` | Перед окончательным завершением, после сбора обычных воркеров |
| `SessionEnd` | После успешной проверки Stop, перед выходом |

`matcher` — имя инструмента/алиас, `|` между вариантами и glob `*`/`?`.
Пустой matcher и `.*` означают все варианты. Для SessionStart сопоставляется
`startup`/`resume`, для SessionEnd — причина завершения; полный regex пока не
реализован. `once: true` снимает hook после одного успешного исполнения в этом
запуске. После нового запроса или перезапуска он снова доступен.

Корневая конфигурация читается один раз перед выполнением модели, вложенные
каталоги skills — при первом обращении к их области.
Изменения конфигурации агентом применятся со следующего запроса. Файлы скриптов
при этом входят в обычную актуальную копию проекта. Hooks не запускаются на
хосте Core: команды проходят через существующую песочницу, с uid владельца,
её сетью и ограничениями. Им доступны JSON stdin и переменные
`CLAUDE_PROJECT_DIR`/`LAYLA_PROJECT_DIR`, `CLAUDE_SKILL_DIR`/`LAYLA_SKILL_DIR`,
`CLAUDE_SESSION_ID`/`LAYLA_SESSION_ID` внутри песочницы.

В stdin находятся `session_id`, `hook_event_name`, `cwd: "."`, а также:
для tool-событий — `tool_name`, `tool_input`, `tool_use_id` и после вызова
`tool_response`; для Stop — `last_assistant_message`, `stop_hook_active`.
При ограничении размера выставляется `input_truncated=true`: hook не должен
принимать отсутствие обрезанных данных за доказательство безопасности.

## Результат hook

Код 0 без вывода означает успех. Обычный текст становится обратной связью.
Структурированное решение возвращается одним JSON-объектом:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Этот путь защищён"
  }
}
```

Для PreToolUse доступны `updatedInput` (объект аргументов) и
`additionalContext`. Аргументы снова проходят обычные проверки инструмента;
режим Confirm показывает уже изменённое действие. `allow` не отменяет права
персоны, режим или обязательное подтверждение Git push. `ask` не создаёт
отдельное окно в Auto: действие блокируется с указанной причиной.

`decision: "block"`, `continue: false`, `permissionDecision: "deny"` или
ненулевой код блокируют pre/prompt/Stop-событие. Перед первым вызовом модели
это завершает запрос с явной ошибкой. Ошибка post-hook передаётся модели;
уже выполненное действие не откатывается. Ошибка SessionEnd сохраняет файлы
и помечает запрос ошибкой. Stop возвращает модель к задаче без «Продолжай»;
разрешены две доработки, затем явная ошибка вместо бесконечного цикла.

Вывод команд сейчас объединяет stdout и stderr. Структурированный JSON нельзя
смешивать с логами: такой ответ отклоняется, а не принимается за разрешение.
Пишите JSON отдельно; команды с обычным текстовым выводом могут возвращать
контекст без структурированного решения.

## Режимы и интерфейс

В Auto hooks выполняются самостоятельно. В Confirm каждая команда требует
подтверждения; «Разрешить всё» действует на текущий запуск. Plan/Review и
персоны без `code.run`/`shell.local` пропускают автоматические команды с явной
пометкой. Skills с чтением инструкций при этом остаются доступны.

Карточки hooks в Code свёрнуты по умолчанию, включая работающие. В строке
видны событие, команда и состояние; вывод раскрывается вручную. Выполненные
команды сохраняются в истории и аудите как `project.agent.run`.
Остановка запроса отменяет текущую команду; после отмены новые Stop/SessionEnd
команды не запускаются. Записи именно hooks остаются в песочнице и пока не
синхронизируются обратно в файлы проекта. Обычный `run_command` и фоновые команды
уже поддерживают возврат результатов — [CODE_SHELL.md](CODE_SHELL.md).

## Пример skill с проверкой перед завершением

`.layla/skills/fix-tests/SKILL.md`:

```yaml
---
name: fix-tests
description: Исправить тесты в отдельной рабочей копии
argument-hint: '[путь к тестам]'
arguments: [target]
context: fork
allowed-tools: [Read, Glob, Grep, Write, Edit, Bash, LSP]
hooks:
  Stop:
    - hooks:
        - type: command
          command: 'python "$CLAUDE_SKILL_DIR/verify.py"'
          timeout: 30
---
Изучи $target. Исправь причину падения, затем запусти тесты.
Верни краткий отчёт о выполненных проверках и оставшихся проблемах.
```

`.layla/skills/fix-tests/verify.py`:

```python
import json
import subprocess
import sys

json.load(sys.stdin)
check = subprocess.run(
    [sys.executable, "-m", "pytest", "-q"],
    capture_output=True, text=True, timeout=20,
)
print(json.dumps({
    "decision": "approve" if check.returncode == 0 else "block",
    "reason": (check.stdout + check.stderr)[-4000:],
}))
```

Вызов: `/fix-tests tests/test_api.py`. В песочнице должны быть установлены
pytest и зависимости проекта; агент может установить их обычным `run_command`.
Пример проверяет весь набор тестов перед завершением, аргумент задаёт область
первичного исследования.

## Пределы и остаток переноса

| Ограничение | Значение |
|---|---|
| Skills в каталоге | До 200 проектных + 3 встроенных |
| Один skill / YAML metadata | 64 КиБ / 16000 символов |
| Активации за запуск | 20; повтор той же пары путь skill/аргументы отклоняется |
| Hooks на запуск | 40 |
| Вызовы hooks / суммарное время | 80 / 300 секунд |
| Таймаут одной команды | по умолчанию 30, максимум 120 секунд |
| Сохранённый вывод hook | 16000 символов; обрезанный результат не считается решением |
| Payload stdin | ограничивается, с `input_truncated` |

Не перенесены prompt/agent/http/async hooks, остальные lifecycle-события,
постоянный реестр hooks между запросами, плагины, глобальные/managed источники,
удалённые/package skills и остальные встроенные команды архива. `/simplify`,
`/skillify`, `/remember` адаптированы под инструменты Layla; это не полная копия
внутренней среды архива. Полная архивная семантика
разрешений не перенесена. Неподдерживаемые execution-поля отклоняются явно.
YAML aliases/anchors/tags и повторяющиеся ключи запрещены. Эти границы отражены
в реестре как `partial`.

После обновления пересоберите core и frontend обычным способом. Core получает
зависимости PyYAML, markdown-it-py, wcmatch и regex; новая миграция БД,
изменение `.env` или новая версия sandbox
для этого этапа не нужны.
