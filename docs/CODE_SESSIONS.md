# Сессия ведущего и его рабочие копии

В Code-чате сохраняется внутренняя история ведущего: запросы, ответы, вызовы и
результаты инструментов. Миграция `0027_code_lead_session` добавляет
`code_lead_turns` и append-only `code_lead_entries`. Журнал привязан к владельцу,
чату и проекту, отдельно от кратких сообщений интерфейса. Следующий запрос
восстанавливает протокол завершённых и прерванных ходов. Системные инструкции
собираются по текущей персоне; при смене провайдера/модели специфичные блоки
reasoning остаются в журнале, но не передаются несовместимому провайдеру.

Если инструмент мог выполнить действие, но результат не записан до аварии,
в контекст добавляется `Outcome unknown`: агент проверяет состояние перед
повтором. Готовые эффекты автоматически не воспроизводятся. Входящая почта
ведущего, включая вопросы во время ожидания воркеров, подтверждается доставленной
в одной транзакции с записью сообщения в журнал.

Откат исключает отменённые ходы из контекста, сохраняя исходные записи для
просмотра. Сводки после точки отката отключаются. Compact включает настоящие
результаты инструментов; он меняет используемое представление истории, а не
удаляет исходный журнал. Ужатие старых сообщений удаляет tool-call/result группы
целиком, чтобы провайдер не получал ответы без соответствующего вызова.

`GET /chats/{chat}/session?offset=…&limit=…` читает журнал страницами по 1–100
сообщений. В UI он свёрнут внутри панели рабочей копии. Сырые сообщения никогда
не используются вместо проверки текущих разрешений персоны, режима и skill.

## Рабочие копии

Миграция `0028_code_workspaces` добавляет `code_workspaces` и привязки контрольных
точек к каталогу копии. В одном Code-чате активна одна копия. Хранилище:

`<parent проекта>/.layla-code-workspaces/<project UUID>/<workspace UUID>/`

Внутри — приватный `repository/` и настоящий Git `worktree/`. Для Git-проекта
локально копируется история без hardlinks и без конфигурации/хуков/ключей
исходного репозитория. Затем копируются текущие файлы проекта, включая ещё не
закоммиченные изменения и удаления. Проект без Git получает локальный snapshot
репозиторий. Фильтры экспорта исключают `.git`, ссылки, special files и кеши
зависимостей; действуют обычные лимиты ZIP проекта.

| Инструмент | Поведение |
| --- | --- |
| `enter_worktree({name?})` | Создать копию, ветку `layla/<name>-<UUID prefix>` и переключить ведущего |
| `exit_worktree({action:"keep"})` | Вернуться в исходный проект, сохранив копию и ветку |
| `exit_worktree({action:"remove", discard_changes?})` | Удалить активную копию; грязные файлы/новые коммиты требуют явного discard |
| `resume_worktree({workspace_id})` | Продолжить в существующей сохранённой копии |
| `worktree_list` | Показать копии именно этого Code-чата |
| `worktree_diff({workspace_id})` | Диф от исходного HEAD, включая коммиты и текущие файлы |
| `worktree_read({workspace_id,path})` | Прочитать точный текст из активной/сохранённой копии |
| `worktree_publish({workspace_id})` | Опубликовать коммиты только в собственную ветку копии |

Переключение происходит внутри одного пользовательского запроса. Файловые,
shell, Git, LSP и worker инструменты перепривязываются к новому каталогу.
Соседние вызовы того же пакета модели после переключения явно пропускаются:
они планировались для прежнего каталога. Модель получает их результаты как
«не выполнено» и делает новый ход. Общие лимиты запросов/ходов/времени не
сбрасываются, сужение инструментов skill сохраняется. Перед переключением
нужно завершить/остановить воркеров и разобрать pending-результаты shell.

Кеши shell/LSP привязаны к UUID копии. Дочерний воркер получает свою отдельную
копию текущего каталога и возвращает правки туда же. Его нельзя возобновить или
применить из другого каталога: сначала нужно вернуться в исходную для него копию.
Контрольные точки также сохраняют идентичность каталога. При недоступной или
удалённой копии откат явно завершается ошибкой, не подставляет основной проект.

## Публикация и UI

`git_commit` внутри копии создаёт коммит в её собственной ветке. `git_push` и
`git_sync` не принимают другую ветку при работе в копии. `worktree_publish`
использует HTTPS remote исходного проекта и учётные данные его владельца;
незакоммиченные правки сначала нужно сохранить. В исходную ветку эта операция
не сливает изменения, force push не выполняется. Создание PR/merge остаётся
отдельной операцией; автоматического PR-контракта в этом этапе нет.

В чате виден текущий каталог агента. Свёрнутая панель позволяет создавать,
сохранять, возобновлять и удалять копии, смотреть файлы/дифы, скачивать ZIP и
публиковать ветку. Основной редактор и проектный терминал продолжают показывать
исходный проект; просмотр копии расположен в её панели. Автоматическое открытие
её diff в основном редакторе отключено, чтобы одинаковые пути не смешивались.

| API | Назначение |
| --- | --- |
| `GET /chats/{chat}/workspaces` | Состав копий и активная привязка |
| `POST /chats/{chat}/workspaces/{enter,resume,exit,publish}` | Прямое действие пользователя |
| `GET /chats/{chat}/workspaces/{id}/diff` | Диф всей копии |
| `GET /chats/{chat}/workspaces/{id}/files?path=…` | Папки или текстовый файл |
| `GET /chats/{chat}/workspaces/{id}/archive` | ZIP без метаданных Git |

Plan/Review предоставляют чтение списка, дифа и файлов. Переходы и публикация
подчиняются `repo.git`, текущему режиму и подтверждениям Confirm. Каждая операция
повторно проверяет владельца/чат/проект. Вручную подложенный `.git` файл не
расширяет доступ серверного Git: допускаются только проверенные маркеры layout
управляемых копий. Удаление в корзину сохраняет копии для восстановления,
окончательная очистка чата убирает также вложенные worker worktrees.

## Остаток соответствия архиву

Рабочие сессии восстанавливаются в собственном формате Layla. Архивные
transcript import/fork, атрибуция строк, полное состояние hooks/compact,
межсессионные peers и bridge, hook-created worktrees, tmux, произвольные ref
и единое переключение основного редактора/проектного терминала остаются.
Не восстанавливаются OS-процессы после перезапуска. Сохранённый журнал и зелёный
CI не означают полного соответствия архиву: статус этих подсистем `partial`.
