# MCP и расписания в Code

Область этого этапа — Code. Плагины отложены по решению пользователя.
Миграции `0032_code_schedules` и `0033_code_mcp_oauth` добавляют расписания,
зашифрованное состояние OAuth и файлы результатов MCP.

## Подключение MCP

Сервер создаётся в «Настройки → Интеграции». Для включённого HTTP-сервера
кнопка «Войти через OAuth» запускает браузерную авторизацию. Поддерживаются
PKCE S256, discovery protected-resource/authorization-server metadata,
клиенты с Client ID Metadata Document, dynamic registration и заранее
зарегистрированный client ID с необязательным secret. Scope можно задать
в дополнительных параметрах. Повторный вход переиспользует регистрацию
клиента, если сервер, issuer и callback не изменились.

Задайте `LAYLA_PUBLIC_URL=https://your-layla.example` — внешний origin без пути.
Callback: `https://your-layla.example/api/code/mcp/oauth/callback`.
Публичные метаданные клиента: `/api/code/mcp/client-metadata`.
Для заранее зарегистрированного клиента callback нужно разрешить у провайдера.
В production origin должен использовать HTTPS; в development возможен HTTP
callback, если его допускает authorization server. Сами MCP OAuth endpoint
и metadata/token endpoints требуют публичного HTTPS.

State привязан к вошедшему владельцу, действует 10 минут и используется один
раз. Verifier, client secret и токены зашифрованы существующим ключом Layla.
Ключ шифрования должен сохраняться при перезапуске. Токены не выдаются модели
или API. Metadata/token-запросы проверяют публичные DNS-адреса, закрепляют IP,
проверяют TLS hostname, запрещают redirect и ограничивают размер ответа.
Bearer отправляется только выбранному MCP resource. Refresh сериализуется
lease/revision в БД; отзыв нельзя отменить завершившимся позже refresh.
При неопределённом результате ротации требуется повторный вход.
«Отключить OAuth» сразу удаляет локальные credentials и по возможности отзывает
токен у провайдера. Вход всегда запускается явным действием пользователя.

Code использует отдельный пул SDK-соединений с привязкой к владельцу, чату,
проекту, персоне и серверу. Соединение сохраняется между сообщениями, закрывается
через 120 секунд простоя или при остановке Core. До 128 соединений на процесс,
очередь до 32 запросов на соединение. SDK-контексты открываются, используются
и закрываются в одной asyncio task. Ошибочный mutating RPC автоматически
не повторяется: результат мог уже быть применён сервером.

`mcp_search_tools` обнаруживает инструменты; `mcp_auth` сообщает состояние входа,
`mcp_reconnect` переподключает сервер. Поддерживаются пагинация ресурсов и
шаблонов, чтение ресурсов, уведомления между раундами и обновление каталога
после `tools/list_changed`. После сбоя следующий вызов может создать новое
соединение; `mcp_reconnect` позволяет сделать это явно. Права владельца,
включённость сервера и доступ персоны проверяются заново при вызовах.

Текст и structured JSON поступают в результат инструмента. Image/audio и
resource blobs сохраняются отдельными файлами с авторизованной загрузкой из
Code-чата. Base64 не попадает в контекст модели. Лимиты: 2 МБ на файл,
6 МБ на ответ, 200 файлов и 64 МБ на чат. Удаление чата удаляет файлы.

Границы: sampling, elicitation, prompts UI, автоматическое повышение OAuth
scope и полное соответствие архивному MCP lifecycle ещё не реализованы.
Транспорт использует текущую зависимость MCP SDK 1.x; отдельный перенос на
новую модель транспорта протокола 2026 не заявляется. Существующие интеграции
других доменов не переведены на этот Code-пул и OAuth.

## Расписания

В Code-чате с проектом откройте панель «Расписания». Можно задать одну дату
в часовом поясе устройства либо пятичастный cron с IANA timezone
(например, `0 9 * * 1-5`, `Europe/Moscow`). У cron есть переключатель повторения.
Режим выполнения выбирается явно; по умолчанию — Confirm. Задача создаёт
обычное сообщение и Job в том же чате, результат появляется в его истории.
Панель позволяет приостановить, возобновить и удалить расписание.

Агенту доступны `cron_create`, `cron_list`, `cron_update`, `cron_delete`.
В Confirm изменение расписания требует обычного подтверждения, и агент
не может создать/возобновить Auto-расписание. В Plan/Review доступен только
список. Прямое управление пользователем через панель может выбрать Auto.
Права персоны и подтверждения действий сохраняются при выполнении задачи.

Cron поддерживает `*`, числа, списки, диапазоны и шаги; воскресенье — 0 или 7.
Если и день месяца, и день недели ограничены, применяется OR. Следующий запуск
ищется в пределах 366 дней. Несуществующее локальное время при переходе DST
пропускается, повторяющаяся минута запускается только в первом вхождении.
До 50 расписаний на чат; после достижения лимита удалите старые.

Core проверяет расписания каждые 10 секунд, до 20 запусков за tick.
Расписания сохраняются в БД. У каждого запуска есть lease 60 секунд и стабильный
request ID: повтор admission после сбоя возвращает существующий Job без
повторной записи сообщения. Это гарантия идемпотентности постановки в очередь,
а не exactly-once внешних действий. Неизвестный результат уже выполнявшейся
задачи обрабатывается обычным механизмом Jobs.

Занятый чат откладывает admission минимум на 30 секунд. Пропущенные за время
простоя повторения объединяются в один запуск; следующий считается от текущего
времени. Разовая задача после admission остаётся в списке выключенной.
При смене проекта или активной рабочей копии расписание отключается с объяснением;
оно не должно незаметно выполнить старую задачу в другой копии. Чтобы возобновить,
вернитесь в исходную копию или создайте новое расписание. Удалённый/недоступный
проект или владелец также блокирует запуск. Рабочий Core необходим: отдельного
внешнего сервиса пробуждения хоста нет.

Удаление/пауза запрещает будущие admission; уже поставленный Job останавливается
обычной кнопкой остановки задачи. Локальные OS-процессы и MCP-сессии не переживают
перезапуск, в отличие от расписаний и OAuth credentials. Существующее ограничение
Core на выполнение Jobs одним процессом сохраняется; lease защищает именно
admission расписаний и OAuth refresh, не превращая Jobs в распределённую очередь.

Отличия от архива: нет jitter, автоматического истечения повторяющихся задач,
режима session-only и маршрутизации расписания конкретному teammate; remote
triggers/sessions и проактивный агент остаются отдельными нереализованными
контрактами.

## Развёртывание и проверка

Пересоберите Core/frontend и выполните обычное обновление схемы:

```bash
cd core
alembic upgrade head
pytest -q tests/test_code_*.py tests/test_project_agent.py tests/test_history.py tests/test_mcp.py
```

Тесты используют настоящий stdio MCP-сервер, проверяют состояние между ходами,
отмену и отсутствие replay, бинарные загрузки и изоляцию, OAuth PKCE/refresh/
revoke/повторный вход и регистрацию клиента. Планировщик проверяется через
настоящие API/БД/Jobs с тестовым provider stream, включая конкурентный tick,
сбой между admission и bookkeeping, busy chat и смену worktree. Миграционный
тест делает upgrade с `0031`, проверяет ORM diff и downgrade без потери пользователя.
Внешний production OAuth-провайдер и живое развёртывание этим не проверяются.
