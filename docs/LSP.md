# LSP в Code

Code использует настоящие language servers через stdio JSON-RPC. Главный агент
и независимые воркеры получают инструмент `lsp`; у каждого воркера свой корень
песочницы, соответствующий его приватной рабочей копии. В остальных доменах
инструмент не подключается.

## Обновление

После обновления кода пересоберите и перезапустите sandbox:

```bash
docker compose build sandbox
docker compose up -d sandbox
```

Обновите core и frontend обычным способом. Дополнительной миграции БД для LSP
нет, существующий `.env` менять не требуется. Проверить доступность можно через
`GET /api/projects/{id}/lsp` или панель анализа в редакторе.

В образ устанавливаются фиксированные версии:

| Язык | Сервер |
|---|---|
| Python (`.py`, `.pyi`) | `python-lsp-server[pyflakes,pycodestyle]==1.12.2` в отдельном `/opt/layla-lsp/python` |
| JavaScript/TypeScript, JSX/TSX, CJS/MJS/CTS/MTS | `typescript-language-server@4.3.3`, `typescript@5.7.3` в `/opt/layla-lsp` |

Python использует Jedi и Pyflakes; стиль pycodestyle по умолчанию отключён.
Это не полная проверка типов Python уровня Pyright/mypy. Установленные в
песочнице зависимости помогают анализу, но не синхронизируются в основной проект.

## Инструмент и редактор

`lsp` принимает относительный `path`, `operation`, `line`, `character` и
необязательный `query` для поиска символов проекта. Входные строки/столбцы
начинаются с 1; столбец измеряется в UTF-16, как индекс textarea в браузере.
Возвращённые диапазоны LSP начинаются с 0, что явно указано в ответе.
Для закреплённой версии Python-сервера есть адаптер её внутренних Unicode
индексов в UTF-16, включая диагностику и переходы через строки с emoji.

| Операция | Поведение |
|---|---|
| `goToDefinition` | Определение символа |
| `findReferences` | Ссылки, включая объявление |
| `hover` | Тип и документация |
| `documentSymbol` | Символы открытого файла |
| `workspaceSymbol` | Символы проекта по `query` |
| `goToImplementation` | Реализации интерфейса/символа |
| `prepareCallHierarchy` | Узел иерархии вызовов |
| `incomingCalls` | Кто вызывает первый найденный узел |
| `outgoingCalls` | Что вызывает первый найденный узел |
| `diagnostics` | Диагностика текущего файла, версия и `ready` |

Поддержка определяется возможностями сервера. Например, Python-сервер может
не поддерживать иерархию вызовов; тогда возвращается явная ошибка. Ответ
`diagnostics.ready=false` означает ожидание анализа, а не отсутствие ошибок.
`stale_source=true` означает, что файл на диске изменился во время запроса.

В редакторе панель «Анализ кода · LSP» свёрнута по умолчанию. Выберите символ
курсором, затем операцию. Переходы используют путь и строку результата.
Существующий несохранённый файл анализируется как черновик через `didChange`,
не меняя файл проекта; новый файл сначала нужно сохранить. Агент всегда
передаёт актуальное сохранённое содержимое, поэтому чужой черновик редактора
не становится его исходным файлом.

Для агента достаточно `files.read`; LSP доступен в Auto/Confirm/Plan/Review
без разрешений на shell или запись. Агент получает рекомендацию применять
семантический анализ перед широким поиском и проверять диагностику после правок.
Решение вызвать инструмент остаётся за моделью.

## Жизненный цикл и границы

Сервер запускается от uid владельца внутри sandbox с ограничениями процесса,
без окружения Core, доступа к БД или API-сокету. Команда запуска задана образом;
запрос не может заменить бинарник, окружение или JSON-RPC метод. Root-сервис
не открывает содержимое файлов проекта: текст поступает от безопасного читателя
Core. `workspace/applyEdit` отклоняется, `workspace/executeCommand` не доступен.

Перед запросом обновляется копия проекта. Изменения/удаления закрывают старые
буферы, уведомляют сервер и сбрасывают кэш диагностики, включая зависимые файлы.
Файлы проекта проверяются no-follow чтением; ссылки и внешние/dependency пути
из результатов отбрасываются, затем повторно проверяются на стороне Core.

Сессии разделены по uid, проекту и языку. Обычная команда не завершает работающий
LSP общим `kill_all`. Сброс песочницы закрывает и серверы. После падения сервера
следующий запрос создаёт новую сессию; остановка запроса завершает её процессы.
Сессия не сохраняет OS-процесс после перезапуска sandbox — он создаётся заново.

| Ограничение | Значение |
|---|---|
| Текст файла | 1 МБ UTF-8 |
| JSON-RPC сообщение | 4 МБ |
| Элементы каждого массива результата | до 100 |
| Размер нормализованного результата | до 100000 символов |
| Открытые документы на сервер | до 64 |
| Таймаут RPC | 30 секунд |
| Ожидание push-диагностики | до 5 секунд |
| Простой / срок жизни сервера | 10 минут / 1 час |
| Серверы всего / на uid | 16 / 8 |

Результаты помечаются `bounded=true`; массивы, глубина и строки ограничиваются.
Это не полный индекс всех символов большого проекта. `query` и точечные
операции позволяют сузить результат.

HTTP API проверяет владельца проекта:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/projects/{id}/lsp` | Установленные серверы и активные сессии |
| POST | `/api/projects/{id}/lsp` | Операция; UI может добавить `content` с черновиком |
| DELETE | `/api/projects/{id}/lsp` | Остановить серверы этого проекта |

## Проверки и оставшийся объём

Тесты запускают настоящие Python- и TypeScript-серверы по stdio, проверяют
определения между файлами, ссылки, hover, символы, реализации, иерархию вызовов
и обновление диагностики. Дополнительные проверки покрывают таймаут, отмену,
повреждённый протокол, перезапуск, лимиты, владельцев, проектные границы и
read-only интеграцию агента в Plan.

Ещё не перенесены конфигурация LSP через плагины, произвольные языковые пакеты,
автоматическая доставка диагностики между ходами и внешний IDE bridge.
Полное соответствие архиву по-прежнему не достигнуто.

Первичные контракты: [LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/),
[Python LSP](https://github.com/python-lsp/python-lsp-server),
[TypeScript Language Server](https://github.com/typescript-language-server/typescript-language-server).
