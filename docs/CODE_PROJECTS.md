# Локальные проекты и файловый агент

Проверяемый объём переноса функций из предоставленного архива описан в
[CODE_PARITY.md](CODE_PARITY.md), полный реестр — в [code-parity.json](code-parity.json).
Это поэтапная реализация; полное соответствие пока не достигнуто.

## Skills и hooks

В чате Code кнопка **Skills** показывает проектные workflows. Выбор вставляет
`/имя` в сообщение; добавьте аргументы и отправьте. Агент может сам вызвать
подходящий workflow через `invoke_skill`. Поддерживаются YAML frontmatter,
`$ARGUMENTS`, `$0`/`$1`, именованные аргументы и `context: fork` для работы в
отдельном воркере. `allowed-tools` сужает набор инструментов, права персоны и
режима остаются обязательными.

Проектные command hooks можно задать в `.layla/hooks.json` или settings-файлах
`.layla`/`.claude`. Они получают JSON в stdin и работают в песочнице. PreToolUse
может запретить действие или исправить аргументы; Stop может вернуть задачу
на доработку. В Auto команды выполняются самостоятельно, в Confirm требуют
подтверждения; Plan/Review автоматические команды hooks пропускают. Карточки
hooks свёрнуты, вывод и ошибки доступны по нажатию.

Форматы, готовый пример и проверяемые ограничения — в
[CODE_WORKFLOWS.md](CODE_WORKFLOWS.md). Для этого этапа нужны обновлённые core
и frontend; новая миграция БД и изменение `.env` не требуются.

## Семантический анализ кода

В редакторе есть свёрнутая панель «Анализ кода · LSP»: определение, ссылки,
hover с типом/документацией, символы файла/проекта, реализации, иерархия вызовов
и диагностика. Установите курсор на символ и выберите операцию; результат
открывает нужный файл и строку. Проверяется текущий черновик без записи на диск.

Инструмент `lsp` доступен Code-агенту и его независимым воркерам при праве
`files.read`, в том числе в Plan/Review. Он читает сохранённые файлы. Серверы
работают в песочнице; для первого набора включены Python и JavaScript/TypeScript.
Если sandbox старый или не запущен, агент не получает неработающий инструмент.

После обновления **пересоберите sandbox**; новая миграция для LSP не нужна.
Подробности и ограничения — в [LSP.md](LSP.md).

## Постоянные задачи Code и notebook

`ask_user` задаёт до четырёх вопросов с одиночным/множественным выбором и
свободным ответом. Вопросы и ответы хранятся в БД. Работающий агент ждёт
ответа и продолжает в том же задании; после остановки интерфейс отправляет
ответы в чат для продолжения. Это вопросы по задаче, а не запросы разрешений
на обычные действия в Auto.

Code-чат поддерживает `task_create`, `task_get`, `task_list`, `task_update`:
задачи с зависимостями, исполнителем, статусом и проверенным результатом
сохраняются в БД между ходами и перезапусками. `memory_write`, `memory_search`,
`memory_delete` сохраняют заметки только этого чата. Сводка доступна в
свёрнутой панели «Задачи чата», отдельной для каждого чата и аккаунта.

Для Jupyter есть `notebook_read` и `notebook_edit` с редактированием отдельных
ячеек, diff, проверкой SHA, подтверждениями и откатом. Plan/Review не меняют
notebook или память. Независимые агенты описаны ниже; в Plan/Review доступны
только роли исследования и ревью, без импорта изменений.

## Независимые агенты и фоновые команды

`agent_start` запускает разработчика (`implement`), исследователя (`explore`)
или ревьюера (`review`) и сразу возвращает ID. Одновременно в одном Code-чате
могут работать до трёх воркеров, включая `command_start` — фоновые команды.
Разработчик меняет собственную копию; остальные роли только читают файлы.
Воркеры не создают других воркеров и не публикуют изменения в Git.

Каждый получает настоящий отдельный Git worktree из снимка сохранённых файлов
проекта, включая незакоммиченные. Это работает и без Git в основном проекте,
его репозиторий и индекс не меняются. Копии находятся рядом с корневой папкой
проекта: `.layla-code-workers/<project UUID>/<worker UUID>/worktree`.
Зависимости, `.git` и ссылки в снимок не входят, как и при экспорте ZIP.

`worker_list`, `worker_output`, `worker_wait` показывают состояние, вывод,
последние инструменты и изменения. `worker_stop` сохраняет готовые правки,
`worker_resume` продолжает агента в прежней копии с сохранённой сводкой.
После перезапуска сервера незавершённая работа помечается прерванной и доступна
для продолжения. Фоновая команда при продолжении исполняется с начала.

Главный агент дожидается обычных воркеров перед финальным ответом, получает
результаты и может проверить и импортировать их без команды «Продолжай».
При отмене главного задания эти воркеры останавливаются. Только явный
`detached=true` оставляет воркера работать независимо от текущего ответа.

`worker_apply` импортирует все или выбранные текстовые изменения с проверкой
SHA каждого файла, дифами и обычными контрольными точками. Если исходный файл
успел измениться, импорт отклоняется: правки редактора и копия воркера остаются.
В Confirm требуется одно подтверждение общего дифа, в Auto импорт выполняется
самостоятельно. `worker_discard` удаляет только копию; для неприменённых правок
нужно явное `discard_changes=true`. После окончательного удаления чата/проекта
его копии очищаются; активные воркеры блокируют удаление до остановки.

В свёрнутой панели «Воркеры» видны активность, отчёт, дифы и кнопки управления.
Вывод и состояние изолированы владельцем, чатом и текущим проектом.
Песочница команд отдельная для каждого воркера; изменения shell пока не
синхронизируются в проект. Импорт ограничен 200 текстовыми файлами и 4 МБ
суммарного содержимого; вывод хранит последние 80000 символов.

MCP-инструменты находятся через `mcp_search_tools` и подключаются к контексту
по мере необходимости. Ресурсы и URI-шаблоны серверов доступны через
`mcp_list_resources`, `mcp_resource_templates`, `mcp_read_resource`.

В разделе **Код → Новый проект → С нуля** укажите название. Layla создаёт пустой
каталог на сервере в `LAYLA_PROJECTS_DIR` (либо в каталоге рабочего пространства).
GitHub, git init и ключ GitHub для этого не нужны. Импорт Git остаётся отдельной
вкладкой. Каталоги получают UUID, поэтому одинаковые названия не конфликтуют.

## Работа с файлами

- Откройте файл в дереве, измените текст и нажмите **Сохранить**.
- **Создать файл** принимает относительный путь, например `src/main.py`.
  Недостающие папки создаются при сохранении.
- Кнопка удаления удаляет один файл после подтверждения в интерфейсе.
- Каждое изменение возвращает настоящий unified diff. При удалении/создании
  пустого файла операция показывается даже при отсутствии строк в дифе.
- Редактор хранит SHA-256 прочитанной версии. Если файл изменили агент или другая
  вкладка, старая версия не перезаписывает новую: API отвечает `409 Conflict`.
  Черновик остаётся в редакторе; нужно перечитать файл и повторить изменение.

На широком экране доступны дерево, редактор и агент одновременно. На узком
экране и в ручном мобильном режиме они переключаются вкладками.

## Агент

Чат постоянно связан с одним проектом. При переключении проекта открывается его
собственная история. Выберите модель с поддержкой function/tool calling и задайте
задачу, например: «Создай Python-проект с README и src/main.py».

Доступны `list_files`, диапазонный `read_file`, `glob_files`, `grep_files`,
`repo_map`, `write_file`, `edit_file`, `append_file`, `delete_file`, публичные
`web_search`, `web_fetch`, `github_search`, проектные skills и до трёх независимых
воркеров с ролями реализации, исследования и ревью. Модель не может выбрать другой корневой каталог. Права выбранной
персоны проверяются сервером: `files.read` разрешает чтение и листинг;
`files.write` — запись, правку, дозапись и удаление. Без персоны доступны все
файловые инструменты. Shell, установка пакетов и запуск тестов идут через отдельную
песочницу проекта; их вывод сохраняется в карточке команды.

- `edit_file` заменяет точный фрагмент (`old_string` → `new_string`, уникальный
  или `replace_all`). Правка «сделай кнопку синей» — несколько строк, а не весь
  файл заново: ответ модели не упирается в предельную длину.
- `append_file` дописывает в конец. Большой новый файл модель пишет частями:
  `write_file` с первой частью, потом `append_file`.
- Если вызов всё же не влез в предельную длину ответа, это не ошибка: ход
  повторяется с просьбой писать частями (до 2 раз).
- `update_todos` — план задачи (чеклист в ответе); доступен любой роли.
- `.layla/skills/<name>.md` хранит повторяемый проектный workflow. Агент сам
  перечисляет и читает подходящий skill, когда он относится к задаче.
- Включённые MCP-серверы из настроек подключаются к Code-чату автоматически с
  отдельным namespace. Ограничение сервера по персоне соблюдается. В Plan/Review
  MCP скрыт; в Confirm каждый вызов ждёт решения, в Auto выполняется самостоятельно.
- Воркер работает в отдельном контексте и собственной рабочей копии. Роль
  `implement` меняет только её; `explore/review` имеют инструменты чтения.
  В чате видна компактная карточка; задача и результат раскрываются по нажатию.

Режимы чата: «Авто», «С подтверждением», «План» и «Ревью» (последние два — только
чтение). Правила проекта — файл `LAYLA.md`, модель видит его в каждом ответе.

Поддерживаются потоковые вызовы OpenAI-совместимого Chat Completions API и нативного
Anthropic Messages API. Части JSON сначала собираются и проверяются целиком.
Незавершённый ответ, превышение токенов или некорректный JSON не выполняют вызов.
Ошибки файловых операций возвращаются модели, чтобы она могла исправить путь
или перечитать версию файла. Модель/шлюз должны поддерживать указанный протокол
инструментов; обычный текст с кодом сам по себе не записывается в проект.

Изменения применяются сразу. В чате показываются действия и раскрываемые дифы,
которые сохраняются после каждой завершённой операции. Ошибка следующего шага
не откатывает уже записанные файлы. История и дифы доступны после перезагрузки.
Кнопка остановки прекращает текущий запрос, сохраняя выполненные изменения.

Страховочные пределы одного запроса — 80 раундов, 400 вызовов и 50 минут. После
них, после ошибки или остановки под чатом появляется «Продолжить»: модель видит,
что успела сделать и почему ход прервался, и продолжает с того же места.

Перед первым изменением файла в ходе его исходное состояние сохраняется
(контрольная точка). У ответа агента — «Откатить к этой точке»: файлы вернутся
к виду до этого ответа, изменения его и всех следующих ответов отменятся, а модель
узнает об откате из истории.

## ZIP

**Скачать ZIP** выгружает сохранённое состояние выбранного проекта с относительными
путями; бинарные файлы и пустые каталоги поддерживаются. Несохранённый текст
редактора в архив не входит. Архив собирается во временном файле и отдаётся
порциями; временный файл закрывается по окончании передачи.

Исключаются `.git`, `node_modules`, `.venv`, `__pycache__`, `.next`, символические
и жёсткие ссылки, специальные файлы. Лимит — 100 МиБ исходных данных и 10000
элементов. Большой архив отклоняется целиком до начала скачивания.

## Границы файлового доступа

Общий файловый сервис используется API и агентом. Он запрещает абсолютные пути,
Windows-пути, `..`, обратные слеши, управляющие символы и доступ к `.git`.
Все операции открывают компоненты пути относительно дескриптора корня с
`O_NOFOLLOW`, не переходят по симлинкам и не работают с устройствами/FIFO.
Текстовый редактор принимает UTF-8 без NUL, до 1 МБ на файл. Запись атомарна;
блокировка каталога сериализует операции Layla между процессами, а SHA защищает
от устаревших изменений. Это Linux/POSIX-реализация под существующее Docker-окружение.

## API и обновление

После обновления выполните обычную миграцию `alembic upgrade head`.
Для воркеров нужна миграция `0024_code_workers`.
Миграция `0007_code_projects` добавляет nullable `chats.project_id`; старые чаты
и проекты сохраняются, старые чаты остаются общими без файловых инструментов.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/projects` | Создать локальный проект (`name`, необязательный `workspace_id`) |
| GET | `/api/projects/{id}/files?path=.` | Список каталога |
| GET | `/api/projects/{id}/file?path=src/main.py` | Текст и `sha256` |
| PUT | `/api/projects/{id}/file` | `path`, `content`, `expected_sha256`: `null` для нового файла, SHA для редактирования |
| DELETE | `/api/projects/{id}/file?path=…&expected_sha256=…` | Удалить файл по прочитанной версии |
| GET | `/api/projects/{id}/archive` | Скачать ZIP |
| POST | `/api/chats` | `domain: "code"`, `project_id`, модель и необязательная персона |
| GET | `/api/chats?project_id=…` | История конкретного проекта |
| GET | `/api/chats/{id}/code-state` | Задачи, память, вопросы и краткое состояние воркеров |
| GET | `/api/chats/{id}/workers/{worker_id}` | Вывод (`offset`, `limit`), отчёт и дифы (`path`) |
| POST | `/api/chats/{id}/workers/{worker_id}/{action}` | `stop`, `resume`, `discard`; удаление неприменённых правок — `?discard_changes=true` |

`POST /projects` больше не принимает произвольный серверный `path`: новые
каталоги выделяет сам сервер. Существующие пути проектов сохраняются.
Файловые API и ZIP проверяют владельца рабочего пространства. Права проверяются
повторно перед каждым запросом чата. В аудит попадают операция и путь, без
содержимого файлов.

## Проверки

Тесты покрывают обход путей, ссылки и их подмену, FIFO, конфликты параллельных
редакторов, изоляцию пользователей, CRUD, ZIP, оба потоковых протокола, обрывы,
лимиты, права персоны, сохранение дифов при ошибке следующего шага и обновление
старой схемы БД. Сетевой провайдер в тестах заменён детерминированными SSE-ответами;
файловые операции и API выполняются настоящие.

## Запуск кода

Агент может выполнять команды в песочнице проекта (`run_command`): ставить зависимости,
запускать тесты, линтеры и сборку, а программы на других языках — в Piston (`run_code`).
Команды работают с копией проекта: их изменения в проект не попадают, файлы меняются только
инструментами файлов. Во вкладке **Терминал** то же самое можно делать вручную, у открытого
файла есть кнопка «Запустить». Подробности, безопасность и настройки — в [SANDBOX.md](SANDBOX.md).
Живое превью запущенного приложения — вкладка **Превью**, там же правка по клику
(подробно — в [SANDBOX.md](SANDBOX.md#превью-приложения)).

## Git

Вкладка **Git** в проекте:

- **Включить Git** — `git init` с веткой `main` (для импортированных проектов уже включён).
- **Изменения** — список файлов и дифф без побочных эффектов (индекс не трогается).
  «Закоммитить всё» записывает все изменения одним коммитом; автор — вы (имя и e-mail из
  профиля).
- **История** — коммиты с диффом каждого по клику.
- **Удалённый репозиторий** — адрес `https://…` (например, пустой репозиторий на GitHub) и
  токен доступа для этого хоста. Токен хранится зашифрованным, один на хост для вашей учётной
  записи; в адрес, конфиг репозитория и логи он не попадает. **Push** / **Pull** — кнопками;
  pull только fast-forward, без слияний.

Агент видит Git проекта: `git_status`, `git_log`, `git_diff` доступны всегда (в «Плане» и
«Ревью» тоже), `git_commit` — в «Авто» сам, в «С подтверждением» после разрешения,
`git_push` **всегда** ждёт вашего подтверждения, в любом режиме. Право роли — «Git»
(`repo.git`), для новых ролей включено. Действия пишутся в аудит (`project.agent.git`,
`project.git.*`).

Безопасность: хуки репозитория не запускаются, локальные пути (`file://`) как удалённый адрес
запрещены, только https. Миграция `0014_git_credentials` добавляет таблицу токенов.
