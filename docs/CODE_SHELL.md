# Команды Code: файлы, фоновые процессы и REPL

## Возврат результатов

`run_command` выполняется в sandbox. Созданные, изменённые и удалённые файлы
возвращаются в исходный проект с дифами и контрольными точками. Сохраняются
байты (включая бинарные файлы и CRLF) и исполняемый флаг. Ненулевой код выхода
не отменяет уже сделанные изменения; результат выполнения сообщается отдельно.

В Auto импорт происходит без дополнительных окон. Confirm подтверждает команду,
затем общий диф импорта; «Разрешить всё» распространяется и на импорт. Plan не
запускает команды. Review может запускать проверки в копии, но не импортирует
их изменения в проект. Наличие `code.run`/`shell.local` не даёт `files.write`.

Каждый импорт проверяет исходные SHA-256 и режим файла. Если редактор или другой
чат изменил файл, пакет сохраняется в sandbox. До его применения или явного
отклонения следующая синхронизация запрещена: результаты не затираются исходными
файлами. `command_changes` показывает пакет, `action=apply` повторяет импорт,
`action=discard` с актуальным `change_id` явно отказывается от него. В терминале
те же действия доступны кнопками. Уже применённые файлы распознаются при повторе.

Все файлы пакета проверяются до первой записи. Каждая запись повторяет CAS под
блокировкой проекта. Если гонка возникла между записями, ранее применённые файлы
и checkpoints остаются, неприменённый остаток доступен для решения. Это не
распределённая атомарная транзакция между файловой системой и БД.

Экспорт запускается отдельным helper-процессом от UID пользователя sandbox.
Сервер не читает содержимое файлов от root. Проверяются обычные файлы без
символических/жёстких ссылок; обход каталогов использует no-follow descriptors.
Ссылки, специальные файлы и недопустимые пути не принимаются за удаления.
Core повторно проверяет пути, содержимое, размеры, хеши и права до импорта.
Проектный код никогда не выполняется в Core.

## Фоновые команды

`command_start` или `run_command(run_in_background=true)` создаёт обычного
Code-воркера в отдельном worktree. Команда сразу возвращает ID; основной агент
собирает результат attached-воркера перед завершением. До трёх активных воркеров
в одном чате. `worker_output/wait` дают вывод и дифы, `worker_stop` останавливает
его процесс, а `worker_apply` импортирует выбранные изменения в главный проект.
Поддерживаются текст, бинарные файлы, удаления и изменение исполняемого флага.

При остановке сохраняются последние полученные stdout/stderr и частичные файлы.
Если сбор пакета не удался, `worker_command_changes` позволяет просмотреть,
повторить сбор в копию воркера или явно отклонить пакет. Только `worker_apply`
меняет главный проект. Возобновление команды запускает её заново в прежней копии;
это не восстановление работающего процесса.

Блокировка sandbox привязана к рабочей копии, а не ко всему аккаунту. Работа
REPL не блокирует соседний проект или независимого воркера. Завершение команды
останавливает её сеанс процессов, не посылая kill всем процессам UID пользователя.
Обычные дочерние процессы и фоновые процессы этого сеанса останавливаются вместе
с командой; намеренно покинувшие сеанс демоны пока не имеют cgroup lifecycle.

## Интерактивный ввод

Пример вызова агентом:

```json
{"command":"python3 -u -i","interactive":true,"timeout":900}
```

Это аргументы `command_start`. Интерактивный воркер автоматически detached:
ожидание ввода не удерживает текущий ответ чата. `command_input` принимает
`worker_id`, точный `text` и необязательный `eof=true`. Для выполнения выражения
нужен перевод строки. В панели воркера доступны ввод, EOF и остановка.

```json
{"worker_id":"<ID>","text":"value = 41\n"}
```

```json
{"worker_id":"<ID>","text":"print(value + 1)\n"}
```

Переменные и cwd сохраняются внутри этого OS-процесса. Доступны Python, Node,
bash и другие установленные программы, работающие через stdin/stdout. PTY нет:
полноэкранные TUI, raw terminal и приложения, требующие настоящий терминал,
не поддерживаются. После остановки/перезапуска память REPL не восстанавливается.

`cwd` команды — относительный каталог проекта; по умолчанию `.`. Отдельные
foreground-вызовы имеют новый shell и не наследуют его переменные или `cd`.
Для общего состояния используйте интерактивный воркер. `shell=powershell`
работает только при установленном `pwsh` в backend; доступные shells публикует
`/sandbox/status`. По умолчанию образ содержит bash. Отсутствие PowerShell
возвращает явную ошибку, без отката к bash и без имитации запуска.

## Терминал и откат

Терминал автоматически собирает допустимые изменения, показывает дифы и историю
импортов. История хранится в `code_shell_runs`, изолирована владельцем/проектом
и переживает навигацию/перезапуск. Она не засоряет общую очередь фоновых задач.
Откат из терминала проверяет версии: более поздние правки редактора не затираются.
В чате применяется обычная кнопка отката ответа. Бинарные checkpoints хранят
base64 и исходный режим файла; старые текстовые checkpoints остаются совместимыми.

## Пределы и обновление

- Пакет: до 200 файлов, 32 МиБ новых данных; файл — до 10 МиБ.
- Снимок: до 20000 записей и 300 МиБ. Каталоги зависимостей/кешей и `.git`
  исключены так же, как при отправке проекта в sandbox. Лимитные/запрещённые
  результаты явно показаны и требуют решения по пакету.
- Команды сохраняют существующий предел `SANDBOX_MAX_TIMEOUT` (по умолчанию
  900 с); интерактивный процесс тоже завершается при таймауте.
- Piston остаётся отдельным запуском standalone-программ, не файловой shell-сессией.
- Command hooks текущего этапа остаются изолированными в sandbox; их записи
  автоматически в проект не импортируются.

Нужны пересборка **core, sandbox, frontend** и миграция
`alembic upgrade head` → `0025_shell_checkpoints`. `.env` менять не нужно.
Старый backend не получает новые функции молча: он остаётся в режиме копии,
а cwd/PowerShell/REPL требуют обновления sandbox.

Полное соответствие Bash/PowerShell/REPL архива всё ещё `partial`: остаются PTY,
автоматический перенос уже работающей foreground-команды в фон, shell snapshots,
профили/правила архива и его отдельный JS primitive-tools kernel API.
