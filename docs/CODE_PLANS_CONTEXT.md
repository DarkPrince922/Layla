# Планы, восстановление контекста, память и бюджеты Code

Этот этап основан на PR #41 и ограничен Code. Плагины отложены.
Миграция `0034_code_control` добавляет планы, checkpoint восстановления,
сводки памяти, compact replay views и реестр расходов. Другие домены не получают
эти инструменты или бюджеты.

## Plan → выполнение

Пользователь выбирает режим Plan либо ведущий вызывает `enter_plan_mode`.
При переходе оставшиеся инструменты текущего пакета не выполняются, runtime
перестраивает разрешённый набор и промпт в режиме только чтения. У ведущего
сохраняются лимиты раундов/инструментов через смену режима и рабочих копий.
Выполнение не возобновляется от текста модели или от вызова submit_plan.
Пока есть pending-план, обычное новое Auto/Confirm-сообщение остаётся в Plan:
для исполнения нужно явное утверждение либо отклонение предложения.

В Plan ведущий вызывает `submit_plan(title, plan)`. Создаётся неизменяемая
запись с владельцем, чатом, проектом, рабочей копией и исходным сообщением.
Остаток пакета не выполняется, ход завершается. Текстовый финальный ответ
в Plan через обычный Job также сохраняется как предложение плана.
Новый план заменяет прежний ожидающий план, сохраняя историю.

Панель Code показывает именно сохранённый текст и три решения:
«Утвердить и выполнить», «Утвердить · подтверждать действия», «Отклонить»
с замечаниями. Последний вариант сохраняет обратную связь для следующего хода.
Утверждение передаёт `approved_plan_id` в обычный `/run`; сервер под блокировкой
чата повторно проверяет scope, pending status, рабочую копию и отсутствие более
новых пользовательских указаний. Решение и создание сообщения/Job коммитятся
вместе. Request ID делает сетевой повтор того же решения идемпотентным.

В Confirm каждая правка по-прежнему ждёт отдельного решения: утверждение
плана не отключает подтверждения и не расширяет разрешения персоны. Текст плана
берётся из БД и остаётся в текущих инструкциях Code после сжатия истории.
Агент должен повторно проверить фактические файлы перед изменением: криптографический
снимок всех файлов при планировании не создаётся, ручные правки проекта возможны.
Статус completed означает завершение хода исполнения, а не независимое
доказательство достижения всех целей плана. При остановке/ошибке — interrupted.

Переход в Plan доступен только ведущему; агент сам не может вернуться в Auto.
Воркеры сохраняют существующий протокол согласования плана с ведущим.
Решения пользователя и режим Confirm проходят через Jobs API, а не legacy
SSE `/messages`; legacy Code Plan/Review остаются только для чтения.

## Восстановление и компактный контекст

Обычный Code Job сохраняет checkpoint вместе с видимым ответом: цель,
последний текст, todos, статусы последних 50 инструментов и рабочая копия.
Checkpoint — ориентир; полный append-only журнал остаётся источником tool
calls/results. При перезапуске неизвестный исход инструмента не становится
разрешением повторить действие: незавершённая группа получает явную ошибку
unknown outcome, агент должен проверить файлы/состояние.

Кнопка «Продолжить с подтверждением действий» передаёт `resume_message_id`.
Сервер проверяет последний действующий interrupted checkpoint, проект,
рабочую копию и отсутствие новых указаний. Продолжение создаёт обычный Job;
повтор с тем же request ID возвращает его. Утверждённый план при продолжении
связывается с новым исполнением. Откатанные/отключённые записи не используются.
Вызов `/run` с обычным новым сообщением также сохраняет существующий replay.

Когда длинный Code-ход не помещается в известный контекст модели, старые
полные группы протокола сжимаются в сводку. Системные инструкции, текущий
запрос и последние два tool-раунда сохраняются. Сводка и граница replay
коммитятся с журналом и acknowledgement почты. Новый экземпляр recorder
использует compact view плюс более поздние записи, не возвращая весь raw
протокол в промпт. Исходные записи никогда не перезаписываются.

`context_search` возвращает исходные действующие записи своего Code-чата:
поиск по тексту, turn_id, пагинация записей и char_offset для длинного результата.
До 30 записей/50 тыс. символов на ответ, до 12 тыс. символов одной записи.
Откатанные ходы исключены. Результаты и сводки — недоверенные справочные данные.
Если сжатие не помогает, Code останавливается с сохранённым прогрессом вместо
молчаливого удаления важных групп текущей задачи. Сводка модели может потерять
детали; для проверки нужно возвращаться к журналу и файлам.

Не восстанавливаются живые OS-процессы, in-memory состояние MCP и вся внешняя
среда. Fork/import не переносит разрешение на исполнение плана или бюджет
исходного чата; это новый чат. Полная совместимость с transcript архива,
все вложения/атрибуция и глобальная managed memory остаются отдельными контрактами.

## Консолидация памяти

`memory_consolidate` сводит существующие заметки своего чата в краткую сводку.
При 20 заметках или суммарно более 12000 символов это также происходит перед
обычным Code Job. Повтор при неизменном fingerprint использует кеш.
Оригинальные заметки, ключи и task graph сохраняются: сводка не удаляет и
не переписывает факты. Изменение памяти инвалидирует digest; результат, который
успел устареть при генерации, не подставляется как актуальный. Контекст использует
валидный digest вместо первых 20 обрезанных заметок. Полные записи доступны
через `memory_search`. Все заметки и сводки остаются недоверенными данными.

Это консолидация явных заметок Code-чата. Автоматическое извлечение новой памяти
из всех разговоров, фоновый dream loop, общая память команды/аккаунта и managed
политики не реализованы.

## Использование и лимиты

В панели «Использование и бюджет» пользователь задаёт общий лимит токенов
и/или USD для чата. Вход/выход текущей модели оцениваются по вручную заданным
ценам USD за миллион токенов; для каждой пары provider/model сохраняются
собственные цены. Цены не загружаются из внешнего каталога и не считаются
счётом провайдера. Кешированные входные токены учитываются по указанной входной
цене; специальные скидки, тарифы и сборы автоматически не вычисляются.

Бюджет един для ведущего, независимых/возобновлённых воркеров, специалистов,
консолидации, сжатия и повторных запросов. Перед каждой сетевой попыткой
CAS-транзакция резервирует вход (консервативная оценка UTF-8 + overhead) и
максимальный выход; другая задача видит этот резерв. Недостаточный бюджет
блокирует отправку следующего запроса. Модель не может менять лимиты.
Смена модели/проекта и сохранение настроек не обнуляют расход.

Usage OpenAI-compatible и native Anthropic нормализуется в input/output tokens,
включая cache-read/cache-creation вход Anthropic, и уточняет резерв. OpenAI
stream_options.include_usage включается только в Code; если провайдер его
отклоняет, используется существующая адаптация параметров. Для других потоков
и провайдеров без usage используется консервативный полный резерв. Точно
отклонённый запрос CapabilityError освобождает резерв. При неизвестном исходе,
отмене или crash резерв сохраняется; это явно отражено в панели.

Бюджеты — ограничение допуска запросов, а не гарантия банковского лимита.
Токенизация оценивается без tokenizer каждого провайдера, сам провайдер может
нарушить output cap или сообщить расход больше резерва. Окончательный usage
может превысить оценку; последующие запросы блокируются. Затраты уже выполняющихся
внешних действий бюджетом LLM не контролируются. Без настроенной цены стоимость
такой модели не входит в историческую USD-оценку; при включённом USD-лимите новый
запрос модели без цены запрещается. Неизвестные резервы автоматически не списываются
как нулевой расход после перезапуска.

HTTP API: `GET /chats/{id}/code-control`, `PATCH .../usage`,
`POST .../plans/{plan_id}/reject`. Все проверяют владельца, домен и текущий проект.
Для запуска выполните пересборку Core/frontend и `alembic upgrade head`.

Отдельный workflow `Code contracts` проверяет миграции на PostgreSQL и Code/
shared-provider тесты независимо от общего workflow репозитория. Локальный
миграционный тест также проверяет upgrade/downgrade SQLite и сохранение данных.
