# Команды и восстановление Code-воркеров

`team_create({team_name, description?})` создаёт одну активную команду в Code-чате.
Ведущий называется `lead`. `agent_start({task, role, name?})` присоединяет агента
к текущей команде; без имени выдаётся уникальное имя. Имена заняты до закрытия
команды, включая остановленных участников. Общий предел прежний: три работающих
воркера на чат, включая команды. Вложенного запуска агентов нет.

`send_message({to, message, summary?})` отправляет текст именованному участнику,
`lead` или всем через `*`. Это внутренняя почта Code, без внешних сервисов.
Рассылка исключает отправителя. Доставка идёт между обращениями к модели;
уже выполняющийся инструмент не прерывается. Когда ведущий ожидает attached
воркера, входящая почта возвращает его к модели для координации, не дожидаясь
завершения участника. Сообщения не расширяют права персоны, режима или skill.

Участник получает свою входящую почту автоматически. `team_info` показывает
состав и переписку; ведущий видит всю команду, воркер — свою входящую/исходящую
почту. Остановленные участники сохраняют входящие сообщения. Для законченного
агента сначала отправляется уточнение, затем вызывается `worker_resume`.
Команда не перезапускает агента автоматически. Возобновление сохраняет ту же
рабочую копию и полную записанную историю диалога и вызовов инструментов.

`team_delete` закрывает команду после остановки всех участников. Это не удаление
их файлов: отчёты, почта, журнал диалога и worktrees сохраняются. Возобновить
участника закрытой команды нельзя; можно создать новую команду. При удалении
самого чата/проекта строки состояния удаляются каскадно обычным механизмом.

В Plan/Review доступен `team_info`; изменение команды и отправка сообщений
через инструменты скрыты. Confirm подтверждает операции команды. API-кнопки
представляют прямые действия пользователя. Чужие аккаунты, чаты и проекты не
могут прочитать команду, её переписку или transcript, даже зная UUID.

## Хранение и восстановление

Миграция `0026_code_teams` добавляет `code_teams`, `code_team_messages`,
`code_transcripts` и имя/команду в `code_workers`. Миграция сохраняет старые
воркеры; при первом продолжении старой записи без журнала используется прежняя
выжимка прогресса. Новые записи журнала добавляются, сжатие model context их
не переписывает. Системный промпт создаётся заново по текущим правам; API-ключи
провайдера в журнал не добавляются.

Сохранение входящего сообщения в transcript и отметка его доставки происходят
в одной транзакции. После жёсткого завершения процесса вызов инструмента может
оказаться записанным без результата. Тогда восстановление добавляет явный
результат `Outcome unknown`: агент должен проверить файлы/состояние перед
повтором, а не автоматически воспроизводить побочный эффект. Это не обещание
exactly-once исполнения команд при аварии ОС.

Вывод 80000 символов и 60 последних tool-событий остаются отдельной краткой
панелью; transcript сохраняет сообщения независимо от этих лимитов. В API
журнал читается страницами по 1–100 сообщений. Сообщение команды ограничено
12000 символами, сводка — 200; максимум 500 недоставленных сообщений на команду.
Автодоставка берёт 50 сообщений за ход. Переписка читается страницами по 50,
в стабильном порядке серверной последовательности.

## UI и API

В Code-чате есть свёрнутая панель «Команда и сообщения»: создание, состав,
адресат, уточнение, переписка, закрытие и архив. В карточке воркера доступен
свёрнутый сохранённый диалог с инструментами и пагинацией.

| API | Назначение |
| --- | --- |
| `GET /chats/{chat}/team?team_id=…&before=…` | Текущая/архивная команда, страницы переписки |
| `POST /chats/{chat}/team/create` | Создать команду |
| `POST /chats/{chat}/team/message` | Отправить уточнение от ведущего |
| `POST /chats/{chat}/team/close` | Закрыть после остановки участников |
| `GET /chats/{chat}/workers/{worker}/transcript?offset=…&limit=…` | Сохранённые сообщения и результаты инструментов |

## Остаток до архива

Это реализация команд внутри Code-чата, а не полный session backend архива.
Остаются структурированные shutdown/plan approval протоколы, peer/UDS/bridge
между сессиями, fork/import чужих transcript, восстановление атрибуции,
контрольных точек compact и настроек/hooks из архивного журнала. У ведущего
по-прежнему обычная история чата; его полный внутренний tool transcript здесь
не восстанавливается. Доставленная ему почта остаётся в БД и доступна через
`team_info` и UI после сбоя. Переключение worktree ведущего и публикация его
ветки также требуют отдельного этапа. Статус соответствия остаётся `partial`.
