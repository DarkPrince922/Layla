# Соответствие Code исходному архиву

Цель — полное функциональное соответствие предоставленному архиву в домене
Code. Полное соответствие **ещё не достигнуто**. Pentest не входит в изменения.
Успешные тесты текущей реализации не означают, что реализован весь архив.

Машинный реестр: [code-parity.json](code-parity.json). Он содержит все **1907**
путей исходного архива, контрольный digest его содержимого, все **40** типов
инструментов и **33** подсистемы. Для каждого инструмента/подсистемы указаны
реализация, статус и конкретные пробелы. Вспомогательные модули, которые ещё
не разложены на поведенческие контракты, отмечены `unclassified`, а не готовыми.

Воспроизвести инвентаризацию:

```bash
python scripts/audit_code_parity.py /path/to/extracted/claude-code
```

Реестр фиксирует имена файлов и digest; исходники архива в Layla не копируются.
`equivalent` означает эквивалент описанного поведения, а не идентичность исходников,
всех граничных случаев или схем аргументов. `partial`, `missing` и `unclassified`
не позволяют объявить полное соответствие.

## Текущий этап

| Возможность | Реализация | Проверка |
|---|---|---|
| Постоянные задачи | `task_create/get/list/update` | Реальные транзакции БД, возобновление в другом экземпляре runtime |
| Зависимости | Граф с `blocked_by`, блокировкой запуска и циклов | Тесты порядка исполнения, циклов и повторного открытия зависимостей |
| Изоляция | Владелец + Code-чат + текущий проект при каждом вызове | Другой аккаунт/чат/проект и удалённый проект не получают состояние |
| Память чата | `memory_write/search/delete` | Сохранение между ходами, параллельные обновления без потери заметок |
| Notebook | `notebook_read/edit` | Изменение одной ячейки, очистка устаревшего вывода, версии, diff, подтверждение и checkpoint |
| Независимые воркеры | До трёх одновременно: реализация, исследование, ревью или фоновая команда | Слоты ограничены БД; запуск четвёртого отклоняется; дочерняя делегация отключена |
| Приватные worktrees | Снимок текущих файлов, включая незакоммиченные, без изменения Git основного проекта | Настоящий `git worktree`, сохранение игнорируемых файлов/CRLF/бинарных входов; работает без Git в основном проекте |
| Импорт правок | `worker_apply`: текст/бинарные файлы/режим, SHA, diff, checkpoint | Конфликт сохраняет ручные правки и копию воркера; Confirm позволяет отклонить весь импорт |
| Прогресс и управление | Свёрнутая панель, вывод, `worker_stop/resume/discard` | Состояние сохраняется в БД, остановка сохраняет рабочую копию; удаление чата очищает копии |
| Завершение делегации | Главный агент собирает результаты перед финальным ответом | Сквозной тест API → главный агент → воркер → импорт без сообщения «Продолжай» |
| Команды и почта | Именованные участники, личные сообщения и рассылка, свёрнутая переписка и архив | Изоляция аккаунтов/чатов, порядок доставки, запрет закрытия работающей команды |
| Восстановление воркера | Append-only диалог с tool calls/results независимо от краткого вывода | Остановка → новый экземпляр → новое сообщение → resume без повторной записи; неизвестный результат после crash |
| MCP discovery | `mcp_search_tools` | В контекст добавляются схемы найденных инструментов, а не весь набор серверов |
| MCP ресурсы | `mcp_list_resources`, `mcp_resource_templates`, `mcp_read_resource` | Привязка к серверам владельца/персоны, пагинация |
| MCP совместимость | Имена до 64 символов, различение коллизий, текст и JSON | Проверки длинных имён, серверов с одинаковыми именами и текстовых ответов |
| Формат skills | `.layla/skills`, `.claude/skills`, `.agents/skills`; Markdown и `name/SKILL.md` | Порядок приоритета, no-follow файловые операции |
| Активация skills | `invoke_skill`, `/имя аргументы`, YAML metadata и буквальная подстановка | Флаги user/model invocation, `allowed-tools` сужает инструменты, метаданные не дают прав персоны |
| Fork skill | `context: fork` через обычные worktree-воркеры | Сквозной API-тест, сбор результата главным агентом и сохранение scope после resume |
| Command hooks | Начало запроса, pre/post tool, ошибка, Stop, завершение | Реальные fixture-скрипты в отдельной копии, deny/update/context, Confirm и отсутствие команд в Plan/Review |
| Ограничения hooks | Snapshot, `once`, `disableAllHooks`, бюджеты, остановка | Повреждённый/смешанный JSON блокирует pre-hook; Stop не зацикливает модель |
| Вопросы пользователю | `ask_user`: до четырёх вопросов, выбор и свободный ответ | Ожидание в том же воркере, ответы в БД, продолжение через UI после остановки |
| LSP | `lsp`: 9 операций архива + диагностика для Python и JS/TS | Настоящие stdio-серверы в sandbox, проверки возможностей сервера, таймауты, отмена и перезапуск |
| Редактор и LSP | Курсор, переходы к строке, символы, проверка черновика | Результаты не пишут файлы, устаревшие ответы скрываются; внешние пути и ссылки отбрасываются |
| Shell → проект | Создание/изменение/удаление, байты/CRLF/режим, durable pending packet | Реальные команды через sandbox protocol, CAS конфликт, запрет затирающей синхронизации, двоичный rollback чата/терминала |
| REPL и фон | Постоянный stdin, EOF, live output, независимые блокировки, остановка | Один процесс сохраняет переменные, соседний воркер продолжает работать, частичные файлы собираются после остановки |
| Сессии и интерфейс копий | Выбор Git ref, редактор/терминал/Git/LSP в активном worktree, импорт JSON/JSONL, экспорт, fork и draft PR | Прямая привязка по чату/владельцу, исходные файлы не меняются; PR использует собственную ветку |
| Протокол команды | Запрос плана, решение ведущего, согласованная остановка, почта между собственными Code-чатами | Структурированные решения в БД, повторная проверка разрешений при продолжении |
| PTY | Интерактивный терминал, размер, ввод и остановка в фоновом воркере | Настоящий TTY сохраняет состояние при переключении вкладок; OS-процесс после перезапуска не восстанавливается |

Состояние задач и памяти хранится в таблице `code_states`, воркеров — в
`code_workers`, с каскадным удалением по чату. Миграции — `0023_code_state` и
`0024_code_workers`. Файлы проекта не используются как база состояния.

Вывод воркера ограничен 80000 символами, последние события — 60. Импортируются
текстовые/бинарные изменения и режимы: до 200 файлов и 32 МиБ суммарного
содержимого до/после. Команды собирают результаты в worktree, главный агент
проверяет и импортирует их. Контракт foreground-команд, REPL и условного
PowerShell — [CODE_SHELL.md](CODE_SHELL.md). Миграция — `0025_shell_checkpoints`.

После перезапуска незавершённый воркер становится `interrupted`: вывод и копия
остаются, продолжение агента использует текущие файлы и записанный диалог с
вызовами/результатами инструментов (для старых воркеров без журнала — сводку),
команда запускается заново. Это не восстановление работающего OS-процесса или
полное воспроизведение transcript архива. `detached=true` позволяет воркеру
продолжить после завершения/остановки главного запроса; обычные воркеры главный
дожидается, а при отмене останавливает.

Задачи чата и память доступны пользователю в свёрнутой панели в Code.
HTTP API: `GET /api/chats/{chat_id}/code-state`. Он проверяет владельца,
домен и доступность текущего проекта. Режимы Plan/Review не получают
`notebook_edit`, `memory_write`, `memory_delete`; задачи можно планировать.

LSP требует пересборки контейнера sandbox, отдельной миграции БД нет.
Контракт, установленные версии, лимиты и проверяемый остаток описаны в
[LSP.md](LSP.md). Поддержка всех методов зависит от возможностей выбранного
language server; отсутствие поддержки возвращается явно, а не как пустой успех.

Контракт hooks/skills, примеры и отличия от архива описаны в
[CODE_WORKFLOWS.md](CODE_WORKFLOWS.md). Команды hooks используют текущую песочницу;
записи именно hooks пока не импортируются в исходный проект. Scope skills сужает
инструменты текущего запуска и наследуется воркером; это не архивная модель
добавочных разрешений. Hooks и skills по-прежнему имеют статус `partial`.

Команды, почта, журнал диалогов воркеров, миграция `0026_code_teams` и точные
границы восстановления описаны в [CODE_TEAMS.md](CODE_TEAMS.md).

Сессия ведущего, переключение рабочих копий, публикация отдельных веток и
миграции `0027_code_lead_session` / `0028_code_workspaces` описаны в
[CODE_SESSIONS.md](CODE_SESSIONS.md).

## Остаток до полного соответствия

Это полный объём требования, а не необязательные предложения:

1. Полная совместимость с журналом архива: атрибуция, все типы вложений и
   состояние compact/hooks; UDS/bridge межсессионных peers и hook-created
   worktrees. Импорт основной ветки JSON/JSONL, fork, выбор Git ref,
   структурированные план/остановка и единая копия редактора/терминала реализованы.
2. Оставшиеся shell-контракты: автоматический перенос уже работающей команды
   в фон, shell snapshots/profiles, cgroup lifecycle покинувших сеанс демонов и
   отдельный JS kernel API архива. Возврат файлов, фоновые команды, вывод,
   остановка, stdin REPL и условный PowerShell уже реализованы.
3. LSP-конфигурация через плагины, произвольные языковые пакеты, автоматическая
   доставка диагностики между ходами и внешний IDE bridge.
4. Остальные события и типы hooks, жизненный цикл плагинов, model overrides,
   динамические/встроенные/удалённые skills, вложенные правила проекта,
   пространства имён и встроенные slash-команды.
5. Переходы Plan → execution и настройки агента.
6. Планировщик, remote triggers, remote sessions, проактивный цикл.
7. Полная память, консолидация, context/continuation/recovery semantics,
   output styles, usage/cost budgets и настройка политик.
8. Полный MCP lifecycle: OAuth, постоянные сессии, уведомления,
   переподключение и двоичные результаты.
9. CLI/terminal/Vim, голос, browser bridge, companion, onboarding, sync
   и остальные пользовательские сценарии архива.
10. Поведенческая классификация оставшихся вспомогательных модулей и
    сквозные приёмочные сценарии для каждой подсистемы.

В архиве нет `package.json`, lockfile или конфигурации сборки. Он также
ссылается на внешние сервисы, чьи серверные реализации в архиве отсутствуют.
Для этих возможностей требуется собственная реализация backend и контракта;
копирование клиентского файла само по себе их не обеспечивает.

Статическая проверка локальных импортов также находит ссылки, для которых
в архиве нет соответствующего файла. Полный список и метод проверки находятся
в `dependency_audit` реестра; генерируемые при сборке модули нельзя восстановить
этой проверкой автоматически. Поэтому реестр фиксирует и эти отсутствующие
зависимости, вместо предположения, что архив можно просто собрать и запустить.
